# ADR-001：TikTok 与 YouTube 使用受控可见浏览器正式发布

- 状态：已接受，待真实账号验收
- 日期：2026-08-11
- 范围：发布中心 TikTok、YouTube 视频通道

## 背景

现有代码已经能够打开官方登录页、保存本地浏览器会话、检测登录态，并把视频与字段
填写到 TikTok Studio 和 YouTube Studio，但正式动作被锁定。直接解除锁定会带来两个
严重问题：按钮点击不等于平台成功；验证码、两步验证和风控页面在后台模式下无法处理。

## 决策

1. 登录只在用户主动点击后打开官方可见窗口。用户自行完成扫码、验证码或 Google 登录；
   客户端只在上传入口或频道后台可用后保存 storage state。
2. 正式发布首版只支持单账号、单视频、立即发布，并强制使用可见浏览器。
3. 发布前继续使用桌面端发布摘要确认。确认结果写入一次性任务载荷，执行器不能绕过。
4. TikTok 只开放公开发布；必须回读文案和公开可见性后才点击 Post。
5. YouTube 支持公开、私密和不公开；必须回读标题、描述、受众、可见性以及已请求的
   可验证字段后才点击 SAVE。
6. 只有明确成功提示，或最终对话框关闭并离开最终按钮状态，才允许任务记为成功。
7. 登录失效、验证码、两步验证、风控、字段回读不一致和未知最终结果都属于安全停止；
   不自动盲目重试，避免重复发布。

## 首版不支持

- TikTok 定时、非公开可见、AI 内容声明、自定义封面。
- YouTube 定时和关闭订阅者通知。
- 两平台多账号或单任务多视频批量发布。

这些字段不能被静默忽略；用户选择后必须在上传前得到明确阻断信息。

## 非功能要求

- 安全：Cookie、storage state、验证码和二维码不得写入日志或仓库。
- 可审计：任务日志记录登录检查、最终点击和平台回执类型，不记录敏感页面内容。
- 可靠性：最终结果不明确时宁可报告失败，也不能误报成功。
- 可维护性：平台 DOM 选择器封装在各自上传器；服务层只处理策略、路由与结果契约。

## 备选方案

- 官方 API：长期更稳定，但需要用户创建开发者应用、OAuth 授权、配额和平台审核；不适合
  当前“免开发者配置”的产品路径。
- 直接复用预检上传器并解除布尔锁：实现最快，但无法保证最终回执，也无法处理安全验证，
  已否决。
- 全后台发布：界面更安静，但验证挑战会造成无反馈卡死，已否决。

## 验收条件

每个平台需使用专用测试账号完成：首次登录、重启后检测、字段回读、立即发布、内容列表
核对、登录过期、验证挑战和失败回执。真实账号验收完成前不得宣称生产稳定。
