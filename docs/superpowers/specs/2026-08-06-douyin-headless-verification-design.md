# 抖音带货无头验证对话框设计

## 目标

在一键发抖音带货正式提交过程中，浏览器始终以无头模式运行。平台出现短信验证码或扫码验证时，客户端以原生对话框承接人工验证，并在同一 Playwright 会话内回读结果后继续；不显示、最小化或前置浏览器窗口。

## 背景与基线

- 源码基线固定为 `2346ffc`。
- `2346ffc` 的后台模式使用真正无头浏览器，并在二次验证时安全停止。
- `1c4bc4b` 改成了有界面浏览器隐藏后再前置，虽然可让用户处理验证，但不符合“后台无感运行”的产品要求；本设计不采用该方案。
- 现有公众号 `wechat_verification` 已证明：二维码可只在本机内存中交给 Qt 对话框，发布线程等待同一请求完成后再继续。抖音实现复用这一线程间协调模式，但不复用微信业务文案、事件名或二维码假设。

## 用户流程

1. 用户已经在一键发完成最终提交确认；执行器使用当前已登录的抖音会话点击平台提交。
2. 页面正常进入作品管理页时，按既有平台回执规则完成，不弹出验证框。
3. 页面出现短信验证时：
   - 执行器唯一识别可填写验证码的输入控件和可提交验证的控件；否则安全停止。
   - 客户端弹出“需要抖音短信验证”，显示平台已发送验证码的说明、仅数字验证码输入框、验证按钮与取消按钮。
   - 用户提交验证码后，代码只在进程内传给当前页面；执行器填写、点击验证并回读成功、错误或仍待验证状态。
4. 页面出现扫码验证时：
   - 执行器只接受可解码、尺寸合理的二维码像素图；图像仅保存在进程内存并由原生对话框显示。
   - 用户扫码后，执行器轮询当前页面的验证完成或发布回执。
5. 平台回读到验证成功后，执行器继续等待原始提交的最终回执；只有实际回读标题、定时或发布状态后才更新任务结果。

## 组件与接口

### 1. `app_core/douyin_verification.py`

新增独立的 `DouyinVerificationBroker`，职责仅是在线程之间传递验证请求和内存态，不保存凭据。

`VerificationRequest` 至少包含：

- `request_id`、`task_id`、`kind`（`sms` 或 `qr`）；
- `message`、`state`、`expires_at`；
- `qr_image`（仅 `qr`，字节仅存内存）；
- `pending_code`（仅 `sms`，仅供同一执行器一次性取走）；
- 页面回读状态和取消标记。

状态只能为 `waiting`、`verifying`、`success`、`expired`、`cancelled`、`failed`。`submit_code` 只接受长度 4 至 8 的数字；它只把验证码暂存到内存，执行器在自己的 Playwright 异步循环中一次性取走并填写页面，避免跨线程调用页面对象。提交前后均不得记录验证码。重复任务请求、未知状态、超时和页面回读异常均转为 `failed`。

### 2. `uploader/douyin_uploader/main.py`

将现有“发现二次安全验证后只记录日志/等待”的分支替换为受控挑战识别：

- 短信分支必须同时找到唯一可见验证码输入框与唯一可见提交控件；将填写、提交与页面回读封装成只在当前 `Page` 使用的回调。
- 扫码分支必须取得唯一有效二维码图片；不从二维码中解析内容、不写入文件、日志或任务载荷。
- 同时存在多种验证入口、控件数量不唯一、验证页面结构未知或二维码不可读时，抛出明确安全错误，不点击猜测控件。
- 无头模式固定保持 `headless=True`，不得调用 `reveal_page_window`、`bring_to_front` 或打开外部浏览器。

### 3. `app_core/douyin_publish_executor.py`

当执行器收到经唯一识别的验证挑战时：

- 记录不含验证码、二维码、Cookie 或页面原始 HTML 的任务事件，例如“抖音需要短信验证，已在一键发等待输入”。
- 通过 Broker 阻塞等待当前验证请求；成功后继续同一页面，不创建新浏览器/新上下文。
- 取消、超时、回读失败或未知挑战抛出 `DouyinPublishError`，任务不得标为已定时或已发布。

### 4. `ui/douyin_verification_dialog.py`

新增原生模态对话框：

- 短信模式：验证码输入、验证、取消、状态提示；不显示或缓存完整手机号。
- 扫码模式：内存二维码、过期倒计时、刷新（仅执行器明确支持时）、取消、状态提示。
- 仅在用户主动点击取消或 Broker 返回终态后关闭；验证成功自动关闭并让执行器继续。
- 不提供“打开验证页面”或任何浏览器前置入口。

### 5. 桌面事件接线

`DouyinCommercePage` 沿用自身的后台任务生命周期，在最终提交任务运行期间以 Qt 定时器按任务号读取 Broker 请求并只创建一个对话框。重复轮询不重复弹窗；终态后清理内存请求。页面关闭或任务取消时调用取消，使执行器安全停止。

## 数据与安全边界

- 验证码、二维码、页面 HTML、Cookie、storage state、请求参数和手机号均不得进入数据库、任务事件、运行日志、发布包、Git 或截图目录。
- 浏览器始终无头；任何需要前台浏览器、登录、验证码之外的新合规/风控提示，停止自动操作并返回可理解原因。
- 本功能不增加账号登录、短信发送、草稿保存、预检绕过或自动发表授权。它只承接用户已经确认的正式提交中平台要求的验证。
- 验证完成不等于发布成功；仍以既有作品管理页/定时状态回读作为任务成功条件。

## 验收与测试

离线测试至少覆盖：

1. 无头启动配置始终为 `headless=True`，且验证路径未调用任何前置浏览器函数。
2. 短信挑战中合法验证码可进入同一页面回调，非数字、过短、过长、取消和超时都会停止。
3. 扫码挑战仅接受有效图片字节；空白、过小、损坏或多二维码候选均拒绝。
4. 控件不唯一、回读不一致和平台错误不会继续提交或写成功状态。
5. 对话框显示短信与扫码状态、取消和终态，且不把敏感值写入可见任务记录。
6. 回归现有抖音带货执行测试及 Qt 离屏 UI 测试。

真实验证需要用户在一次已明确授权的抖音正式提交中自行输入短信验证码或扫码；验证前不启动真实平台会话，验证后仍须以平台最终回执判断结果。
