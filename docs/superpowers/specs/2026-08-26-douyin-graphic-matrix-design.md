# 抖音图文矩阵发布设计

日期：2026-08-26

状态：书面设计待用户复核

适用分支：`integration/oneclick-0.5.0`

## 1. 背景与目标

已确认的客户需求是：同一套抖音图文素材发布到多个抖音账号，各账号的关键词方向相近，但标题、正文、话题和定时可以单独调整。

当前代码已有下列基础：

- `oneclick-content/v1` 图文包、图片序列和平台覆盖字段；
- 发布中心的多账号选择、通用内容和平台适配字段；
- 抖音图文素材上传与标题/描述回读预检；
- 受控任务、一次性授权、心跳/租约收口、暂停/继续和任务明细。

当前缺少的是一条独立、可用的“一套图文 × 多个抖音账号”正式发布链路。本设计的目标是：

1. 为抖音图文矩阵提供独立工作流；
2. 一套图片只保存一份，最多选择 20 个抖音账号；
3. 支持通用内容与单账号覆盖；
4. 支持统一起始时间、账号间隔和单账号定时；
5. 每个账号只打开一次平台会话，在同一会话内完成页面检查、填写回读和受控提交；
6. 单账号失败不阻塞后续账号，失败账号可单独重试。

## 2. 范围与非目标

### 2.1 首版范围

- 仅支持抖音图文，`contentType=article`；
- 每批 1–35 张公共图片；
- 每批 1–20 个抖音账号；
- 通用标题、正文、话题与单账号覆盖；
- 统一起始时间、默认 30 分钟间隔与单账号定时覆盖；
- 本地批量检查、整批正式确认、串行执行、验证暂停、手动暂停、恢复、失败单独重试和结果表；
- 桌面 UI、本机 CLI/MCP 和内容项目调用共用同一发布服务。

### 2.2 非目标

- 不支持每个账号不同的图片集；
- 不在客户端中自动生成 20 套标题或正文；
- 不做多平台图文矩阵；
- 不实现代理 IP、设备指纹伪装、自动登录或风控规避；
- 不把本地检查、页面回读或按钮点击写成已发布。

## 3. 产品入口与界面

发布中心新增独立入口“抖音图文矩阵”，不与“抖音带货”或通用图文页混合。工作流分三步。

### 3.1 内容准备

- 上传一套公共图片；
- 填写通用标题、正文和话题；
- 选择抖音账号，仅显示已保存的抖音账号；
- 图片路径和哈希只记录一份，不按账号复制素材。

### 3.2 账号设置

表格每行对应一个账号，显示：账号、标题、正文、话题、发布时间和配置来源。

每个可覆盖字段都保存独立的 `isOverridden`。规则如下：

1. 未手动修改的字段实时跟随通用内容；
2. 手动修改后标记为“单独设置”，后续修改通用内容不再覆盖它；
3. 点击“恢复通用设置”只重置当前行的指定字段；
4. 任务确认后保存有效内容快照，此后页面再修改不影响已确认任务。

定时规则：

- 日期默认为北京时间当前日期加 1 天；
- 起始时间默认沿用发布中心的 `18:00`；
- 账号间隔默认 30 分钟；
- 单行时间可覆盖自动排期；
- 起始时间或间隔改变时，只重算没有单独覆盖的行。

### 3.3 检查与提交

默认“批量检查”只检查本地可确认事项：图片存在且可读、图片数量、字段长度、结构化话题、账号 ID、定时格式和任务快照。它不登录平台，不能被写成“平台预检成功”。

本地检查后用表格显示每个账号最终会使用的标题、正文摘要、话题和发布时间。用户对整批快照确认一次后，才能启动正式任务。

## 4. 数据合同

不改变基础内容包的职责。`oneclick-content/v1` 继续只保存内容和素材，不保存本机账号。矩阵配置使用独立的本机任务信封：

```json
{
  "schemaVersion": "oneclick-douyin-graphic-matrix/v1",
  "workflow": "douyin-graphic-matrix",
  "runtimeMode": "local_check",
  "content": {
    "manifestPath": "/absolute/path/manifest.json",
    "manifestSha256": "...",
    "images": ["/absolute/path/01.jpg"],
    "common": {
      "title": "...",
      "body": "...",
      "tags": ["..."]
    }
  },
  "targets": [
    {
      "itemIndex": 1,
      "accountId": 4,
      "overrides": {
        "title": null,
        "body": null,
        "tags": null
      },
      "scheduleTime": "2026-08-27 18:00",
      "timezone": "Asia/Shanghai"
    }
  ]
}
```

该信封不接受账号文件路径、Cookie、密码、验证码或二维码。`accountId` 必须在客户端数据库中解析为已保存的抖音账号和独立浏览器资料目录。

任务创建时将公共内容与每行覆盖合成“有效负载”并写入不可变快照。正式发布授权必须绑定下列快照摘要：

- 工作流和任务 ID；
- 内容包哈希和图片哈希；
- 账号 ID 有序列表；
- 每个账号的有效标题、正文、话题和定时。

## 5. 模块边界

首版按下列边界实现，具体文件名可在实施计划中根据现有命名调整：

1. `ui/douyin_graphic_matrix_page.py`
   - 三步表单、账号覆盖表、本地检查结果和任务明细；
   - 不直接操作 Playwright，不自己维护发布线程。
2. `app_core/douyin_graphic_matrix_service.py`
   - 规范化任务信封、解析覆盖、排期、快照和重试子任务；
   - 创建“每个账号一条任务明细”，不按图片数量乘倍生成明细。
3. `app_core/douyin_graphic_editor.py`
   - 唯一负责抖音图文页面的打开、图片上传、标题/正文填写、官方话题选择、定时设置、字段回读、最终提交和平台回执读取；
   - 现有 `_douyin_graphic_preflight` 与新正式执行器都调用这一适配器，不复制两套选择器。
4. `app_core/douyin_graphic_matrix_executor.py`
   - 逐账号串行编排；
   - 使用现有 `account_browser_service`、验证交互、暂停恢复、心跳和租约收口；
   - 当前账号取得明确终态后才进入下一账号。
5. 现有 `publish_service.py`、`task_service.py`、受控 CLI/MCP 和桌面 UI
   - 共用同一个任务创建和执行入口；
   - UI 和本机接口不能分别实现页面发布逻辑。

## 6. 任务和数据库

复用现有 `publish_tasks`、`publish_task_items` 和 `publish_task_events`。矩阵任务的父任务 `payloadJson` 保存完整快照，明细表每个账号一行。

`publish_task_items` 增加下列缺失字段：

- `accountId INTEGER`：稳定绑定本机账号；
- `errorCode TEXT`：可机器读取的稳定失败码；
- `receiptJson TEXT`：平台回执、作品 ID、定时时间和读回证据；
- `authorizationSnapshotHash TEXT`：当前行必须与整批授权快照一致。

重试不修改原任务。系统根据原任务的 `revisionSourceTaskId` 和 `batchItemIndex` 创建只包含失败或未开始账号的新任务；已成功账号不能进入重试快照。

## 7. 预检、授权和账号风控

### 7.1 两种检查的名称和边界

- **本地批量检查**：默认执行，不打开平台；
- **完整平台预检**：仅作为可选测试模式，使用与正式发布相同的图文页面适配器，但绝不定位或点击最终提交按钮。

首版默认不对 20 个账号执行“完整平台预检一次，正式发布再打开一次”，避免同一批账号重复访问后台。

### 7.2 正式授权

正式发布必须使用客户端对当前不可变矩阵快照生成的短期一次性授权。授权仅允许“对快照中的账号执行页面检查，检查通过则提交该账号”，不允许替换账号、素材、内容或定时。

这是矩阵工作流相对现有“先完整平台预检，再重新打开正式发布”的明确改动。现有通用发布和抖音带货的授权规则保持不变；只有 `workflow=douyin-graphic-matrix` 使用这个“确认后即时页面检查，通过才提交”合同。实施时必须同步项目规则和授权测试，不能静默放宽现有通道。

授权令牌在任务启动时消费。验证码等待和官方 60 秒冷却属于已启动任务内的暂停，完成后可自动继续。用户手动暂停后，必须点击“继续发布”才恢复。客户端异常退出后不自动沉默提交，剩余账号须由用户在客户端确认继续。

### 7.3 账号会话

- 始终只运行一个抖音账号页面；
- 使用该账号已保存的独立资料目录，不退出再重新登录；
- 同一会话中完成打开图文页、图片上传、字段与话题回读、定时回读和最终提交；
- 取得平台明确回执或明确失败后关闭页面与临时会话，再启动下一账号；
- 登录失效时不自动输入凭据；任务明细记录失效并继续检查后续账号；
- 首版不提供“多开数量”和“风控调速”选项。

## 8. 平台填写和回读合同

每个账号的页面操作顺序固定：

1. 打开抖音图文发布页并确认当前账号；
2. 上传 1–35 张公共图片并确认数量回显；
3. 清理旧标题和旧正文，填入当前账号的有效内容并回读；
4. 逐个搜索并点选官方话题候选；
5. 回读每个话题的平台实体状态，不允许普通 `#文字` 降级冒充；
6. 设置立即发布或定时发布，回读北京时间；
7. 再次回读图片数、标题、正文、话题实体和时间；
8. 只有全部一致时才定位并点击最终按钮；
9. 从平台提示或作品管理页回读平台回执、作品 ID 或定时时间。

缺少第 9 步的平台证据时，该账号不得标记为发布成功。

## 9. 任务状态和恢复

父任务状态：

`draft -> locally_checked -> awaiting_confirmation -> running -> paused | success | partial_failed | failed | cancelled`

账号明细状态：

`pending -> checking_session -> preparing_page -> awaiting_verification | submitting -> scheduled | success | failed`

规则：

- 单账号失败时立即写入终态和错误信息，然后继续后续 `pending` 账号；
- 验证码窗口显示当前账号和序号，验证码不隐藏；
- 60 秒重发冷却使用实时倒计时，冷却结束自动继续当前账号；
- 手动暂停只在当前平台动作安全收尾后生效，已获得回执的账号不会重复提交；
- 进程退出、线程异常或心跳租约过期时，运行中和未开始项必须收口为失败或可恢复暂停，不得永久 `running/pending`；
- 整批结束后，只能对失败或未开始账号创建新的重试任务。

生命周期图：[docs/architecture/douyin-graphic-matrix.lifecycle.html](../../architecture/douyin-graphic-matrix.lifecycle.html)

## 10. 结果明细和错误码

任务明细表最少显示：序号、账号、有效标题/正文摘要、计划时间、当前阶段、状态、错误码、失败原文、平台回执/作品 ID 和重试操作。

稳定错误码优先复用现有等价错误，缺少时新增：

| 错误码 | 含义 |
| --- | --- |
| `douyin_graphic_matrix_invalid` | 矩阵信封或有效负载无效 |
| `douyin_graphic_account_session_expired` | 当前账号登录失效 |
| `douyin_graphic_entry_missing` | 当前页面没有可唯一识别的图文入口 |
| `douyin_graphic_image_upload_failed` | 图片上传数量或回显不一致 |
| `douyin_graphic_title_readback_mismatch` | 标题回读不一致 |
| `douyin_graphic_body_readback_mismatch` | 正文回读不一致 |
| `douyin_topic_entity_missing` | 目标话题没有成为平台官方实体 |
| `douyin_graphic_schedule_readback_mismatch` | 定时回读与快照不一致 |
| `douyin_graphic_verification_cancelled` | 用户取消当前账号验证 |
| `douyin_graphic_submit_receipt_missing` | 执行最终动作后没有取得平台回执 |
| `controlled_worker_lease_expired` | 受控进程失联，任务由租约机制收口 |

验证码等待和手动暂停是状态，不是失败码。

## 11. 本机接口

桌面 UI、CLI 和 MCP 都通过 `publish_service` 创建相同任务。内容项目可以：

1. 提交结构化内容包与矩阵目标；
2. 创建默认的本地检查任务；
3. 读取 `taskId` 和每个账号的检查结果；
4. 将已检查快照交给客户端供用户确认；
5. 有一次性授权时启动正式任务并轮询 `taskId`。

本机接口默认只能创建 `local_check`。不能因为由 Codex 或内容项目调用就跳过客户端的整批确认和一次性授权。

## 12. 测试与验收

按项目测试阶梯执行：先复现/失败测试，再最相关单项，再受影响模块，最后才是全量和离屏客户端。

### 12.1 本地自动测试

- 1 个和 20 个账号的任务信封、明细数量与排期；
- 通用字段跟随、单字段覆盖、恢复通用设置和快照不受后续界面修改影响；
- 公共图片只存一份，任务明细不按图片数乘倍；
- 错误账号不阻塞后续账号；
- 验证暂停、60 秒冷却、手动暂停、继续和已成功账号不重复执行；
- 进程异常、心跳过期和客户端退出后不留永久 `running/pending`；
- 重试快照只包含失败和未开始账号；
- UI、CLI 和 MCP 产生相同的规范任务快照。

### 12.2 源码客户端验收

- 三步界面和 20 行账号表不挤压、不丢字段；
- 本地检查不打开任何抖音页面；
- 使用伪平台页证明每个账号仅创建一次会话；
- 失败、验证、暂停和任务结果在明细表中正确显示；
- 离屏客户端可启动，范围检查和 `git diff --check` 通过。

### 12.3 真实平台验收

真实平台验收使用已授权的测试账号，先单账号、再少量多账号：

1. 完整平台预检证明图片数、标题、正文、官方话题实体和定时都能回读，且没有执行最终提交；
2. 只有用户对当次快照明确授权后，才执行少量账号的正式发布；
3. 必须取得每个账号的平台回执、作品 ID 或定时时间读回，才标记对应成功层级；
4. 少量真实账号稳定后，再单独进行 20 账号容量验收，不在首次平台试验中直接全量执行。

## 13. 实施切片

一个实施计划内按下列顺序交付：

1. 矩阵信封、快照、数据库明细和本地检查；
2. 独立三步 UI 与账号覆盖/排期表；
3. 共用抖音图文页适配器，先接通完整平台预检；
4. 串行矩阵执行器、验证/暂停/恢复和任务明细；
5. 一次性授权的矩阵快照绑定与正式提交；
6. CLI/MCP 入口、失败单独重试、全量回归和真实平台分阶段验收。

实施前必须先完成本书面设计复核，再使用 `superpowers:writing-plans` 拆分逐任务实施计划。
