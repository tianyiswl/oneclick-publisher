# 抖音带货地点 DOM 作用域修复设计

## 背景与问题

抖音带货批量任务 `T08081532-EBB7` 共 19 条，11 条取得作品管理页的定时成功回读，8 条在地点步骤失败。6 条失败提示地点输入框“实际 9 个”，2 条提示无法唯一识别“位置”入口。

运行代码会从整张发布页收集可编辑字段，再逐个向上查找同时包含唯一“本地/国内”标签的祖先。地点弹层与发布页其他字段共享较大的祖先容器时，标题、文案、定时等字段也会被算作地点输入框。现有 portal 测试直接模拟页面返回 `count=1`，没有执行真实 DOM，因而没有覆盖该现场结构。

## 目标

1. 地点输入框只能从“本地/国内”标签对所属的最小地点弹层中产生。
2. 发布页存在其他可编辑字段时，仍能唯一识别地点输入框。
3. 动态“位置”入口短暂未完成渲染时允许有限等待；始终不在歧义状态下猜测或点击。
4. 无法唯一确认时继续安全停止，不降低现有发布保护。
5. 不改变批量任务、定时、声明、音乐、最终提交或平台回执逻辑。

## 方案选择

采用“最小地点弹层 + 唯一输入框 + 有限稳定等待”方案。

不采用 CSS 类名或 placeholder 直连方案，因为这些展示属性更容易随平台版本变化。不采用全页候选打分方案，因为它可能在高分相近时误填标题、文案或其他字段，不符合发布自动化的失败关闭原则。

## 详细设计

### 1. 地点输入框作用域

地点输入框查找按以下优先级执行：

1. 如果已经唯一标记的带货地点控件本身是可编辑输入框，直接使用该控件。
2. 否则在可见 DOM 中寻找精确文字叶节点“本地”和“国内”。
3. 每一对标签先求最小公共祖先，再从该祖先向上有限层级寻找候选容器。
4. 候选容器必须同时满足：
   - 只包含一对可见“本地/国内”标签；
   - 只包含一个可编辑输入字段；
   - 该输入字段确实是候选容器的后代；
   - 候选容器不是 `document.body`，也不能扩展到包含多个发布表单字段的大容器。
5. 全页只能得到一个候选地点弹层和一个候选输入框；零个或多个均返回明确歧义并安全停止。
6. 旧版 `anchor-item` 内嵌输入框继续保留为后备，但只有 portal 路径没有候选时才能使用。

这会把搜索方向从“每个输入框是否共享地点标签祖先”改为“地点标签对所在最小容器是否只有一个输入框”，从源头消除 9 个字段被一起纳入的问题。

### 2. 动态位置入口

`_ensure_position_tag()` 在初次未找到唯一位置入口时，不立即猜测。它最多进行短时、有限次数的只读回读：

- 每次重新运行现有的唯一位置入口检测；
- 只有返回唯一候选时才允许点击；
- 多候选、页面结构异常或等待结束仍无候选时保持原错误并安全停止；
- 不增加全页模糊文字点击，也不通过序号选择。

有限等待只处理抖音动态渲染的瞬态，不掩盖真实结构歧义。

## 数据流与错误处理

批量执行器仍按“上传 → 音乐 → 声明 → 地点搜索 → 精确 POI 匹配 → 定时 → 预检 → 最终提交”执行。本修复只发生在地点搜索的控件发现阶段。

- 成功：返回唯一地点输入框，继续现有范围切换、关键词填写和完整 POI 匹配。
- 未渲染：有限等待后再次读取。
- 零候选：返回原有可诊断错误并安全停止。
- 多候选：立即视为歧义，不点击、不填写、不提交。

失败条目不会进入定时同步、预检或最终提交；已成功条目的状态与平台回读不受影响。
