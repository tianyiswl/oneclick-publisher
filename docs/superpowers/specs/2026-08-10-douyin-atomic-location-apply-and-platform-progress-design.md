# 抖音带货正式发布地点原子应用与平台设置进度条设计

状态：方案 A 已确认，待用户审阅书面设计

日期：2026-08-10  
范围：一键发开发版「抖音带货」正式发布地点回读链路与平台设置底部进度反馈

## 1. 已核实现象

2026-08-10 批次 `T08100006-D236` 的本机任务数据证明，本次不是第二步数据未保存：

- 20 条视频均已写入完整 `locationPoi`，包含可见 POI 身份、名称、完整地址与 `domestic` 范围。
- 第 1 条在正式发布会话重新搜索时，未从当次候选中匹配到预设。
- 第 2—5 条已在搜索结果中匹配预设，但在后续重新打开地点面板并点击时，页面未找到唯一目标。
- 5 条均在上传、标题/文案回读、音乐与声明之后，地点应用阶段失败；没有进入最终提交。
- 连续失败 5 条后任务已按现有安全门自动暂停，后续 15 条保持未开始。

当前暂停任务不自动恢复、不重发失败项，也不用作修复后的默认验证样本。

## 2. 根因

现有正式发布地点链路被拆成两个不连续的页面动作：

1. 批量执行器调用 `search_locations()` 读取当前关键词候选。
2. 会话管理器在候选读取完成后主动关闭地点面板。
3. 批量执行器在本地用 POI 或名称+地址匹配保存的预设。
4. 随后调用 `apply_location()`，服务层再次打开地点面板并尝试点击。

第 4 步重新打开后，平台不保证保留第 1 步的关键词、筛选范围和候选快照。因此本地已匹配的候选可能不在重新打开的页面列表中，造成“数据已保存，正式页点击不到”。

## 3. 目标与非目标

### 3.1 目标

1. 正式发布时，在同一个已打开的地点面板中连续完成搜索、匹配、点击和回读。
2. 点击前仍要求 POI 或名称+规范化完整地址唯一匹配，不降级为店名模糊匹配。
3. 任何地点不唯一、页面重绘或回读不一致，只失败当前视频并保留精确阶段，不触发最终提交。
4. 平台设置底部为所有耗时采集动作显示真实、不伪造百分比的进度反馈。
5. 旧代际、旧采集器实例或已取消任务的迟到回调不得覆盖新进度。

### 3.2 非目标

- 不恢复、改写或自动续发 `T08100006-D236`。
- 不将已失败的 5 条追写为成功。
- 不为地点匹配增加店名近似、第一条默认选中或无限重试。
- 不修改三个隔离采集器、严格关闭屏障和逐视频新正式会话的总体架构。
- 不在进度条中显示 Cookie、账号路径、原始异常、DOM 或页面 HTML。

## 4. 正式发布地点原子应用

### 4.1 单一公开动作

批量执行器不再分别调用“搜索地点”和“应用地点”。正式会话管理器新增单一公开动作：

```text
apply_saved_location(session_id, preset, scope, keywords)
    -> { location, matchedKeyword }
```

输入只包含当前视频的完整地点预设、国内/本地范围和有界关键词列表。关键词仍由批量执行器依据既有白名单规则生成，会话层不自行扩展或模糊化。

### 4.2 同面板原子流程

单次 `apply_saved_location` 必须在同一个后台任务和同一正式 Page 中串行完成：

1. 关闭进入动作前遗留的旧地点面板。
2. 用第一个有效关键词打开地点面板、确认范围、清空旧输入、写入新值并回读。
3. 在面板保持打开时读取当前候选，使用既有 `match_location_preset` 规则匹配唯一地点。
4. 匹配失败时，先安全收口本轮面板，再进入下一个有界关键词。
5. 匹配成功时，不关闭、不重新打开面板；直接从当前候选列表中重新限定名称+完整地址唯一节点并点击。
6. 点击后回读带货模式与已选地点名称，再由会话层回读完整地点身份。
7. 仅当回读与当次匹配候选一致时返回成功；否则当前视频失败。
8. 失败、取消和异常路径均在 `finally` 中尝试关闭候选面板，清理失败不得被记为应用成功。

候选 DOM 不跨方法、不跨 Page 保存。应用层只传递公开地点字段，不传递 locator、element handle 或页面节点。

### 4.3 执行器门禁

每条视频仍按以下顺序执行：

```text
新正式会话
-> 上传并回读标题/文案/标签
-> prepare_publish_settings 干净基线
-> 音乐回读
-> 声明回读
-> apply_saved_location 原子搜索与应用
-> 排期回读
-> 预检
-> 最终提交与平台回执
```

`apply_saved_location` 未返回完整且唯一的地点回读时，排期、预检和最终提交都不得执行。本条失败后由现有 `finally` 关闭正式会话，再由连续失败门决定是否暂停后续条目。

## 5. 平台设置底部进度条

### 5.1 展示位置与样式

在平台设置页底部 `platform_review_dock` 中，位于状态文字和“返回内容/检查并继续”按钮之间，增加与内容准备底栏同视觉层级的进度块。

进度块包含：

- 当前动作：例如“正在准备国内地点采集”、“正在刷新收藏音乐”或“正在搜索本地点”。
- 已等待时间：按单调时间计算，每秒刷新，不受系统时钟调整影响。
- 动态进度条：使用 Qt 不确定进度模式，不显示伪造的 0—100%。

完成后隐藏进度块，在既有三采集器状态栏显示实际候选数和耗时。失败后也隐藏进度块，但保留固定错误码、重试入口和诊断摘要。

### 5.2 覆盖动作

进度块覆盖所有单队列平台采集动作：

| 动作 | 显示文案 |
| --- | --- |
| 进入平台设置并启动国内采集器 | 正在准备国内地点采集 |
| 刷新收藏音乐 | 正在刷新收藏音乐 |
| 搜索本地点 | 正在搜索本地点 |
| 搜索国内地点 | 正在搜索国内地点 |
| 受控重试某采集器 | 正在重试收藏音乐/本地点/国内地点 |

关闭代际不伪装成候选采集进度，继续使用底部状态文字“正在关闭平台设置采集器…”。

### 5.3 进度所有权与迟到回调

页面只保留一个 `PlatformCollectorProgressState`：

```text
setupGenerationId
collectorType
actionToken
actionLabel
startedMonotonic
```

开始动作时写入该状态并启动 1 秒定时器。成功、失败或结束回调只能在以下三项全部一致时收口当前进度：

```text
callbackGenerationId == progress.setupGenerationId
callbackCollectorType == progress.collectorType
callbackActionToken == progress.actionToken
```

这与现有代际/类型/实例回调门禁互补：采集候选只能由当前实例写入，进度块只能由当前动作收口。旧任务迟到的 `finished` 不得隐藏新任务进度。

途中放弃、登录失效、代际替换、关闭完成、客户端退出和页面重置使用显式 `reset_platform_collector_progress()` 停止定时器、清空所有者并隐藏进度块。

## 6. 错误处理与用户反馈

地点失败继续使用阶段明确、不泄露 DOM 的公开文案：

- `publish_location_candidate_missing`：当次搜索未返回已保存地点。
- `publish_location_candidate_ambiguous`：当次面板有多个同身份候选。
- `publish_location_click_failed`：唯一候选已找到，但页面无法可信点击。
- `publish_location_readback_mismatch`：点击后回读与目标不一致。
- `publish_location_cleanup_incomplete`：失败路径的面板未能安全关闭。

客户端任务明细应显示视频序号、视频名、地点名称、北京时间排期、固定错误阶段和安全说明。错误不再笼统说成“数据保存失败”，也不把候选缓存或平台设置选择写成已发布。

连续失败 5 条的现有自动暂停门保留不变。若同一批前两条出现同一个地点结构错误，本设计不自动放宽匹配；由任务明细和诊断日志保留证据。

## 7. 测试与验收

### 7.1 地点原子应用

先用失败测试确定性复现“搜索后关闭面板，重开后候选消失”：

1. 旧流程在第一次候选中能匹配，重开列表后无唯一目标，测试必须失败。
2. 原子流程在同一面板中搜索、匹配和点击，只点击一次唯一目标并回读成功。
3. 第一关键词无匹配、第二关键词唯一匹配时，第一面板必须先收口，第二面板成功点击。
4. 多个同身份候选、页面点击失败、回读不一致和清理失败均不进入排期、预检或提交。
5. 每条视频仍使用唯一正式会话，上一条失败后在 `finally` 关闭，不污染下一条。

### 7.2 进度条

1. 国内采集器启动、音乐刷新、国内/本地搜索和单采集器重试都显示正确动作文案。
2. 进度条为不确定模式，等待时间每秒增加，不显示伪造百分比。
3. 成功、失败和当前动作正常结束后收口，候选数与耗时保留在采集器状态栏。
4. 旧代际、旧实例、旧 action token 的迟到成功、失败或 `finished` 都不得收口新动作进度。
5. 放弃、登录失效、代际替换、关闭完成、页面重置和客户端退出均清空进度所有者与定时器。
6. 进度运行期间防止同一队列重复操作，但不阻塞 Qt 主线程。

### 7.3 回归与真实验收边界

- 定向测试按先失败、后最小修复执行。
- 平台设置 UI、隔离采集器、会话严格关闭、批量执行器和完整离线回归全部通过。
- 通过 `py_compile`、离屏 `NATIVE_DESKTOP_UI_OK` 和 `git diff --check`。
- 离线测试只证明代码边界，不证明平台当时候选或正式提交成功。
- 如需实机确认，必须在离线门全通过后取得 Andy 当次明确授权，仅用 1 条测试视频、1 个地点执行到地点回读，停在预检/最终提交前并放弃临时页。

## 8. 实施边界

预计只修改以下责任边界：

- `app_core/douyin_commerce_batch_executor.py`：正式地点步骤改为单一原子公开动作。
- `app_core/douyin_commerce_session.py`：组织同会话、同面板搜索与应用。
- `app_core/douyin_commerce_service.py`：拆出“在已打开当前候选中点击唯一地点”的窄职责帮助器。
- `ui/douyin_commerce_page.py`：进度状态、定时器、三重收口门禁和重置入口。
- `ui/common.py`：仅增加平台设置进度块样式，不改全局进度条。
- 对应离线测试文件。

不修改账号登录态、音乐缓存结构、地点预设表、已暂停任务数据和最终平台回执规则。
