# 抖音带货批量受控续发设计

## 背景

当前“暂停发布”只在运行中的批次内生效：当前视频安全收束后，后续视频保持 `pending`，任务标记为 `paused`。客户端没有从历史任务继续的入口。

不能把所有暂停任务直接恢复。登录、短信验证、平台最终提交回执不明和连续失败的暂停，均可能需要用户处理或存在重复发布风险。续发功能必须只处理可证明未开始的视频，并继续保持“平台最终提交须由用户明确确认”的边界。

## 目标

1. 仅允许“用户手动暂停”的新批量任务继续发布。
2. 续发时只处理原任务仍为 `pending` 的视频。
3. 原任务的成功、失败、暂停状态和逐条回执不可改写。
4. 续发任务独立可审计，明确关联来源任务。
5. 每次续发仍需要用户在客户端进行一次新的最终确认。

## 非目标

- 不自动重试任何 `failed` 视频。
- 不恢复短信/登录暂停、回执待核对暂停或连续失败自动暂停。
- 不为历史 `paused` 任务猜测暂停原因；历史任务默认不可续发。
- 不复用浏览器 Cookie、编辑器会话、上传状态、地点候选或音乐抽屉状态。
- 不在本次功能中修改平台提交、回执判定或任务详情表格的既有成功口径。

## 方案选择

采用“新建续发子任务”方案。

### 不采用：原任务原地继续

原任务会混入首次与后续尝试，成功、失败、暂停和再次执行的时间线难以审计；重新运行还可能覆盖原有条目状态。

### 不采用：从草稿重新建批次

虽然现有草稿恢复可让用户手动重建批次，但不会自动筛选未开始视频，也没有来源任务关联，容易漏选或重复选择。

### 采用：独立续发子任务

保留来源任务作为不可变历史。系统仅从其中抽取允许续发的 `pending` 项，创建新的 `oneclick_resume` 批量任务。新任务拥有自己的逐条状态和平台回执，并通过来源任务 ID 关联回原任务。

## 暂停分类与资格

`publish_tasks` 新增 `pauseReasonCode` 字段，允许值固定为：

- `user_request`：用户在客户端主动点击暂停；唯一可续发类型。
- `waiting_login`：账号登录失效或需要重新登录；不可续发。
- `waiting_verification`：短信/扫码验证等待或失败；不可续发。
- `receipt_ambiguous`：最终提交后未获得唯一平台回执；不可续发。
- `auto_failure`：连续失败触发安全暂停；不可续发。

只有同时满足以下条件时，任务才可续发：

1. `workflow == "douyin-commerce-batch"`；
2. 任务状态为 `paused`；
3. `pauseReasonCode == "user_request"`；
4. 至少有一条 `publish_task_items.status == "pending"`；
5. 来源任务保存的逐视频 payload 快照可重建为批次信封，且所有待续发素材仍可通过本地契约校验；
6. 所有待续发的定时时间仍晚于当前北京时间。

缺少任一条件时，任务详情不显示续发按钮；服务层也必须拒绝调用，不能仅依靠前端隐藏按钮。

历史任务没有 `pauseReasonCode`，统一视为不可续发。这样不会用旧事件文案猜测安全状态。

## 数据模型

`publish_tasks` 增加：

- `pauseReasonCode TEXT`：暂停原因；仅暂停任务写入。
- `resumeSourceTaskId INTEGER`：续发子任务的来源任务 ID；普通任务为空。

`publish_task_items` 不增加恢复状态字段。续发任务仅创建源任务中原状态为 `pending` 的新条目，保持原 `batchItemIndex`，使用户仍看到原批次中的视频序号和排期位置。

来源任务追加审计事件：`batch_resume_created`，内容包括续发任务号和续发条数。续发任务创建事件为 `batch_resume_created`，内容包括来源任务号和原视频序号列表。

## 服务边界

新增 `task_service.prepare_douyin_batch_resume(task_id, now)`，只做本地读取与校验。它从来源任务保存的逐视频 payload 快照重建批次共享字段和仅含 pending 项的批次信封，返回：

- 来源任务基本信息；
- 仅包含 `pending` 视频的受控批次 payload；
- 原视频序号列表；
- `resumeAllowed`、阻止原因和待续发数。

它不得创建任务、写任务事件、启动浏览器或访问平台。

新增 `task_service.create_douyin_batch_resume(task_id, now)`，只能接收已通过准备校验的续发请求：

1. 重新读取并重复资格校验，避免界面与数据库状态之间的竞态；
2. 创建 `mode="oneclick_resume"` 的新批量任务；
3. 写入 `resumeSourceTaskId`；
4. 保留源 `batchItemIndex`、地点和原定时时间；
5. 写入来源与子任务的审计事件；
6. 返回子任务和用于执行的纯本地 payload。

来源任务不改变状态、计数、条目状态或原错误消息。

现有 `mark_task_paused` 改为要求显式 `pause_reason_code`。批量执行器在每个暂停分支写入对应代码；用户主动暂停写 `user_request`。

## 界面与流程

1. 用户在“任务记录”打开符合资格的抖音带货批量任务。
2. 明细窗口显示按钮“继续未开始的 N 条”。其他暂停原因和历史暂停任务不显示。
3. 点击按钮只发出“准备续发”请求，由主窗口切换到“抖音带货”页。
4. 抖音带货页显示续发确认弹窗：来源任务号、待续发视频数和原视频序号、原发布方式与定时时间；失败项不在列表中。
5. 用户点击“确认继续发布 N 条”后，才创建续发子任务并启动批量执行。
6. 新任务每条视频都使用新浏览器会话，重新上传、重新回读地点/音乐/声明/定时，再等待作品管理页回执。
7. 用户取消确认、校验失败或排期过期时，不创建续发任务，也不触发平台动作。

主窗口负责把任务详情的续发请求路由到 `DouyinCommercePage`。任务详情组件不直接启动执行器，避免任务列表页面拥有平台执行权限。

## 定时规则

续发绝不自动改期：每条待续发视频沿用来源任务的显式 `scheduleTime`。若其中任何时间已过，北京时间校验失败并提示用户新建批次或手动调整排期；不会把旧时间替换为“明天 16:00”。

## 错误处理

- 任务不存在、不是批量任务、不是用户手动暂停或没有 pending 项：拒绝并给出本地原因。
- 本地媒体不存在、地点身份不完整、音乐/声明无效、账号不可用：拒绝，不创建子任务。
- 定时时间过期：拒绝，不自动调整。
- 点击确认后创建子任务失败：显示原因，来源任务保持原样。
- 子任务运行过程中再次暂停：按新的 `pauseReasonCode` 记录；只有再次为 `user_request` 时，未来才可能继续其自身的 pending 项。

## 测试设计

新增服务与原生界面回归：

1. 用户手动暂停且有 pending 项，可生成只含 pending 项的续发准备数据。
2. 登录、验证、回执待核对和连续失败暂停均被服务层拒绝。
3. 历史 `paused` 任务因缺少暂停代码被拒绝。
4. 续发任务保留原视频序号、地点和定时时间，且来源任务状态、计数和条目状态不变。
5. 任一待续发定时已过期时拒绝，不创建任务，不改期。
6. 来源任务无 pending 项时拒绝。
7. 续发按钮只在符合资格时可见；取消确认前不调用创建服务或执行器。
8. 确认后创建 `oneclick_resume` 子任务，并且最终提交仍经过现有批量执行器与平台回执门。
9. 现有手动暂停、回执待核对、连续失败暂停和批量详情测试保持通过。

## 验收边界

- 本轮不对任何历史暂停任务执行续发。
- 真实平台验证只在未来由 Andy 对一条明确的“用户手动暂停”测试批次点击最终确认后进行。
- 本次开发验证仅覆盖本地任务数据、离屏 Qt 和模拟会话；不能把自动化测试写成平台已续发成功。

## 设计自审

- 规格字段已经完整：暂停代码、资格、子任务关系、排期和确认动作均已定义。
- 不把手动暂停与回执待核对混为同一恢复路径。
- 原任务保持不可变，子任务独立审计，避免成功状态被覆盖。
- 最终发布始终需要用户在当次界面明确确认。
- 范围限于抖音带货批量任务的受控续发，不改平台自动化实现。
