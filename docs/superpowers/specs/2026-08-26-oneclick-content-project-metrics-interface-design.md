# 一键发内容项目数据回收接口设计

日期：2026-08-26  
范围：一键发集成线；五个内容项目只作为本机 MCP 调用方  
架构图：`docs/architecture/oneclick-content-project-metrics-dataflow.html`

## 1. 目标

把过去“发布下一篇时人工截图前一天数据”的动作改成稳定的本机数据通道：平台账号只由一键发读取；内容项目通过一键发 MCP 获得属于自己的发布作品指标和账号级数据快照。

本轮完成源码、数据库、MCP/CLI 合同和离线验证。不会执行真实平台同步、预检或正式发布；真实运行仍需之后使用当前已登录账号做一次只读同步验收。

## 2. 已确认事实

- 一键发已有抖音、小红书、快手、B站和公众号五个平台的只读采集器，视频号尚未注册。
- `platform_data_sync.sync_account_data` 已统一编排平台读取、失败记录、批次持久化和资源清理。
- SQLite 已保存账号指标、作品列表、作品累计指标、同步来源、观察时间和失败状态。
- 内容项目 MCP 当前只有账号、项目档案、预检、授权、正式发布和任务查询，没有数据同步与数据读取工具。
- 普通正式发布任务没有持久化 `projectId` 归属，因此共享账号下无法安全判断某篇作品属于哪个内容项目。

## 3. 方案选择

### 方案 A：一键发统一采集，内容项目通过 MCP 读取（采用）

平台页面变化只修改一键发采集器。内容项目不保存 Cookie、不直接读取一键发数据库，也不会因为项目数量增加而重复访问同一账号。

### 方案 B：五个项目各自调用平台

每个项目都要维护登录、验证、页面变化和失败语义，重复访问同一账号，长期维护成本和触发验证的概率最高，不采用。

### 方案 C：内容项目直接读取一键发 SQLite

短期代码最少，但会把数据库表结构变成跨项目公共接口；数据库迁移会同时破坏五个项目，也难以做项目作品隔离，不采用。

## 4. 总体数据流

1. 内容项目使用现有发布档案创建正式发布任务。
2. 一键发在任务创建成功后原子登记 `projectId ↔ taskId`，不保存正文、Cookie 或登录会话路径。
3. 固定时间自动化通过本机 stdio MCP 请求项目数据同步。它不要求桌面 GUI 一直打开。
4. 一键发把项目映射解析成账号列表，对同一账号执行北京时间当日去重和失败冷却，然后串行调用现有采集器。
5. 采集结果继续写入现有 `platform_data_sync_runs`、`platform_metric_snapshots` 和 `platform_contents`。
6. 查询接口只把该项目正式任务中已经取得平台作品 ID 的作品，与指标快照做匹配后返回。
7. 账号级趋势单独标记为 `scope=account`，不能冒充某个内容项目带来的结果。

## 5. 为什么不把定时器放在桌面窗口

桌面客户端可能没有打开，依赖窗口定时器会漏跑。固定时间由 Codex 自动化或内容项目自动化调用 MCP；“同一账号当天是否已经同步、失败多久后才允许重试”由一键发统一决定。这样五个项目即使同一时刻发起请求，同一账号也只会真正采集一次。

## 6. 持久化

新增表 `content_project_task_links`：

- `projectId`：经过现有项目标识规则校验；
- `taskId`：一键发发布任务 ID；
- `phase`：只允许 `preflight` 或 `formal`；
- `createdAt`：带时区时间；
- 唯一键：`projectId, taskId`；
- `taskId` 外键随任务删除而清理。

只有 `formal` 任务进入作品指标归属集合。预检关联可以保存用于审计，但不能产生作品或指标结果。

既有历史任务不自动猜测所属项目。需要补录时必须由内容项目显式提供已知 taskId，并通过项目账号映射校验后登记；本轮不提供批量自动迁移。

## 7. MCP 接口

### `oneclick_sync_project_metrics`

输入：

- `project_id`

行为：

- 解析项目已配置账号；
- 同一账号同一北京时间日期已有 `success/partial_success` 时返回 `reused`，不再次访问平台；
- 最近一次失败不足 30 分钟时返回 `cooldown`，不立即重试；
- 其他情况串行调用现有 `sync_account_data`；
- 失败不清空上一次成功快照。

输出：`projectId`、`startedAt`、`finishedAt`、每个账号的 `action/status/errorCode/sourceMode/metricCount/contentCount/latestSuccessAt`。

### `oneclick_get_project_metrics`

输入：

- `project_id`
- `days`：只允许 `1/7/30`，默认 `1`

输出：

- 每个项目账号的周期汇总、同步新鲜度和最新同步状态；
- 该项目正式任务已回读作品 ID 的作品指标；
- 每篇作品带 `taskId/platform/accountId/contentId/publishedAt/metrics/availability/observedAt/localSyncedAt`；
- 找不到指标时返回 `availability=missing`，数值为 `null`，不得写成 `0`。

### `oneclick_metrics_sync_status`

输入：

- `project_id`

输出：

- 每个账号最近一次尝试、最近一次成功时间、当前是否处于当日复用或失败冷却；
- 不启动浏览器，不触发平台访问。

三个接口均不接受 Cookie、密码、验证码、会话路径、平台原始响应或数据库路径。

## 8. CLI 与 MCP 的关系

内容项目默认使用 MCP。MCP 与命令行都调用同一个 `ContentProjectGateway`，不能各写一套查询逻辑。命令行只增加用于排错和自动化兼容的动作：

- `metrics-sync`
- `metrics-get`
- `metrics-status`

命令行仍只输出稳定 JSON；平台运行日志进入 stderr，不能污染 stdout 协议。

## 9. 错误和并发

- 未配置项目：`content_project_profile_not_found`；
- 项目没有可采集账号：`project_metrics_accounts_unavailable`；
- 同步正在进行：`project_metrics_sync_busy`；
- 平台采集失败：保留现有数据采集错误码；
- 本地写入失败：`sync_persist_failed`；
- 任务不属于项目账号：`content_project_task_account_mismatch`；
- 作品回执尚无平台 ID：只返回 `missing`，不制造作品 ID。

账号同步锁以 `accountId` 为粒度，GUI 手动同步和 MCP 同步必须共用。一个账号失败不阻止其他账号完成；最终结果按账号逐项返回。

## 10. 安全与数据边界

- 只读数据同步不扩大正式发布授权，也不能创建预检或正式任务。
- 不在 MCP、CLI、日志、项目台账或 Git 中暴露登录会话和平台响应原文。
- 项目查询以 `projectId + taskId + accountId + platform contentId` 四层校验，不能按标题模糊归属。
- 共享账号的账号级数据可以返回，但明确标记为账号整体数据；作品级数据只返回当前项目任务关联作品。
- 当前五个平台采集器的真实可用程度不同。离线测试通过后只能称为源码接口可用，不能称为五个平台已经完成真实同步。

## 11. 实施切片

1. 为项目任务关联、账号同步策略和项目指标查询先写失败测试。
2. 增加数据库表和最小服务层，不修改现有采集器字段语义。
3. 在 `ContentProjectGateway` 登记任务关联并提供三个数据方法。
4. 在 MCP 和桌面 CLI 暴露同一方法。
5. 运行数据监测、网关、MCP、数据库受影响测试；稳定后运行完整测试和离屏客户端。
6. 本轮不升级客户端版本、不打包；是否进入下一版本由完成验证后另行决定。

## 12. 验收标准

- 同一账号同一天由两个项目请求同步，平台采集函数只执行一次，第二个项目得到 `reused`。
- 最近失败不足 30 分钟时不会反复采集；超过冷却后允许下一次尝试。
- 一个项目不能读取共享账号上另一个项目任务对应的作品指标。
- 发布任务成功创建后能读回项目关联；正式任务取得作品 ID 后能返回指标。
- 预检任务、失败任务、没有作品 ID 的任务不能冒充已发表作品。
- 失败同步保留上次成功快照；缺失字段保持 `null/—`。
- MCP 工具合同没有敏感参数，CLI 与 MCP 返回同一数据结构。
- 受影响测试、完整测试、离屏客户端和 `git diff --check` 全部通过。

## 13. 本轮不做

- 不增加视频号采集器；
- 不自动同步评论正文；
- 不做跨账号或跨项目增长归因；
- 不把发布成功立即等同于已有表现数据；
- 不执行真实平台同步、预检、正式发布或重复提交任务 51。
