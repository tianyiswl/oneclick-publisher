# 一键发抖音评论洞察设计

## 1. 当前事实与目标

当前一键发的数据监测页只能显示评论数量，不能读取或查看评论正文。现有 `DouyinDataCollector` 只取得账号趋势，返回 `contents=()`、`content_data_available=False`，因此抖音作品列表和评论正文都还没有可用的数据合同。

本轮新增的是“评论洞察”，不是“评论管理”。目标是让用户在数据监测页选择一篇自己的抖音作品，手动同步最新评论，查看不含作者身份的原评论，并生成附有原评论证据的下期选题候选。

本设计只完成只读链路，不在抖音执行回复、删除、点赞、发布或其他写操作。

## 2. 首轮范围

首轮只支持：

- 平台：抖音；
- 对象：当前一键发中已登录账号的一篇已发布作品；
- 触发方式：用户选择作品后手动点击“同步最新评论”；
- 评论：一级评论正文、点赞数、回复数、评论时间和所属作品；
- 洞察分类：质疑、认同、真实经历、追问、选题建议、其他；
- 选题输出：最多 5 个下期选题候选，每个候选必须引用一条或多条本地真实评论；
- AI：用户配置的 OpenAI 兼容服务，可不配置；不配置时仍可同步和查看评论。

首轮不包含：

- 评论回复、删除、点赞、置顶或私信；
- 评论作者头像、昵称、用户 ID、主页地址或粉丝信息；
- 二级回复正文，只保留平台返回的回复数量；
- 后台定时拉取评论正文；
- 自动发布队列、固定时间账号数据同步和其他平台评论；
- 竞品评论、非本人账号评论或绕过登录与验证。

## 3. 必须先完成的真实数据合同确认

抖音作品列表目前未接通，不能直接猜接口、路径或响应字段。实现第一步必须使用一键发已有登录会话进行一次真实只读合同确认：

1. 打开官方创作者后台的作品数据页和某篇作品评论页；
2. 只观察官方页面自己发起的 HTTPS JSON 响应；
3. 确认作品列表与评论列表的官方域名、固定路径、分页游标和必要字段；
4. 将固定路径和白名单字段写进采集合同；
5. 验证报告只记录阶段、字段名、数量和固定错误码，不记录作品 ID、评论正文、Cookie、请求头、查询串或原始响应。

如果真实账号没有出现可验证的作品或评论响应，功能保持“作品数据暂未取得”，不得用 DOM 文本、猜测接口或复用发布页数据伪装成功。

## 4. 模块边界

### 4.1 现有模块调整

- `app_core/douyin_data_collector.py`：在真实合同确认后补上作品列表，只负责作品元数据与作品指标，不承担评论洞察。
- `app_core/platform_data_models.py`：继续作为作品与指标的公开合同，不混入评论正文模型。
- `app_core/database.py`：增加评论同步、评论证据和洞察运行表的迁移。
- `ui/data_monitor_page.py`：增加作品单选、评论洞察面板和人工同步入口。

### 4.2 新模块

- `app_core/douyin_comment_collector.py`：使用已保存登录会话，只读读取所选作品的评论分页响应，并输出受控评论批次。
- `app_core/comment_insight_models.py`：定义评论、同步结果、分类结果、选题候选和固定错误。
- `app_core/comment_insight_service.py`：负责编排分页、去重、事务保存、查询和 AI 调用边界。
- `app_core/comment_ai_provider.py`：封装 OpenAI 兼容请求、结构化响应校验和证据映射。
- `app_core/comment_ai_secret_store.py`：只通过 macOS Keychain 或 Windows Credential Manager 保存 API Key。

评论采集器不复用发布执行器，也不保留发布页面。每次人工同步创建一个短生命周期会话，完成、失败或取消后都必须关闭页面、上下文和浏览器。

## 5. 评论采集合同

### 5.1 输入

采集器只接收：

- 一键发账号 ID；
- 平台类型 `3`；
- `platform_contents` 中已验证的抖音作品稳定 ID；
- 本次同步上限 100 条一级评论。

作品标题不用于定位作品，不能用标题、封面或发布时间做模糊匹配。

### 5.2 接受字段

单条评论只接受：

- 平台稳定评论 ID，用完即转换为本地匿名评论键；
- 评论正文；
- 点赞数；
- 回复数；
- 评论时间；
- 所属作品稳定 ID。

作者对象及其所有字段在解析入口立即丢弃。平台评论 ID 不落库；本地 `commentKey` 使用账号、作品和平台评论 ID 生成确定性 SHA-256，只用于去重和本地证据引用。

评论正文中的字面内容保持原样。如果用户自己在正文里写了 `@某人`，它仍属于用户已授权同步的原评论正文，但程序不会额外解析、保存或发送该被提及者的身份字段。

### 5.3 分页和停止条件

- 首次同步从最新评论开始，最多接收 100 条有效一级评论；
- 后续同步仍从最新评论开始，遇到第一个本地已知 `commentKey` 后停止继续翻页；
- 停止前已经返回的已知评论会更新点赞数、回复数和 `lastSeenAt`；
- 同一批次重复评论只保存一次；
- 达到 100 条时记录 `comment_limit_reached`，表示本轮安全截断，不表示平台已经加载完；
- 某次响应没有出现已验证的分页入口时停止，不模拟滚动或猜测下一页；
- 本次未返回的历史评论不删除，也不推断为平台已删除。

## 6. 本地数据

### 6.1 `platform_comment_sync_runs`

| 字段 | 含义 |
| --- | --- |
| id | 本地运行 ID |
| accountId | 一键发账号 ID |
| platformType | 固定为抖音平台类型 |
| contentId | 所选作品稳定 ID |
| sourceMode | `direct_session` 或 `browser_signed` |
| status | `running`、`success`、`failed`、`cancelled` |
| errorCode | 固定错误码，成功为空 |
| acceptedCount | 本轮接受的有效评论数 |
| insertedCount | 新增评论数 |
| updatedCount | 更新计数的已知评论数 |
| rejectedCount | 合同不合格的评论数 |
| pageCount | 实际读取页数 |
| stopReason | `known_comment`、`limit_reached`、`platform_end` 或空 |
| startedAt / finishedAt | 本地运行时间 |

### 6.2 `platform_comments`

| 字段 | 含义 |
| --- | --- |
| id | 本地主键 |
| accountId / platformType / contentId | 所属账号、平台和作品 |
| commentKey | 不可逆的本地匿名评论键 |
| body | 原评论正文 |
| likeCount | 平台返回的非负点赞数 |
| replyCount | 平台返回的非负回复数 |
| commentedAt | 平台评论时间 |
| firstSeenAt / lastSeenAt | 本地首次和最近观察时间 |
| lastSyncRunId | 最近更新该评论的同步运行 |

`accountId + platformType + contentId + commentKey` 唯一。同步运行和评论写入使用同一数据库事务；写入失败时不留下半批评论，也不能把运行标为成功。

### 6.3 `comment_insight_runs`

| 字段 | 含义 |
| --- | --- |
| id | 洞察运行 ID |
| accountId / platformType / contentId | 所属对象 |
| status | `running`、`success`、`failed`、`skipped` |
| errorCode | 固定 AI 错误码 |
| providerType | 固定 `openai_compatible` |
| modelName | 用户配置的模型名 |
| promptVersion | 提示合同版本 |
| schemaVersion | 输出结构版本 |
| inputFingerprint | 本轮评论键与正文的本地摘要 |
| commentCount | 实际参与分析的评论数 |
| classificationsJson | 通过校验的评论键与多标签结果 |
| candidatesJson | 最多 5 个候选及其评论证据键 |
| startedAt / finishedAt | 本地运行时间 |

不保存原始 AI 请求、原始 AI 响应、思维过程、API Key 或完整服务地址。数据库只保存已通过本地结构和证据校验的结果。

## 7. AI 数据边界与证据校验

### 7.1 配置

用户配置：HTTPS 基础地址、模型名和 API Key。基础地址与模型名可保存在本机普通设置中；API Key 只进入操作系统凭据库，不写 SQLite、JSON、日志、诊断报告或任务记录。

如果系统凭据库不可用，程序拒绝保存 API Key，并将 AI 状态显示为“未配置”；评论同步仍可正常使用。实现阶段需要把系统凭据库依赖纳入 macOS 与 Windows 打包测试。

### 7.2 发送内容

外部 AI 只收到：

- 所选作品标题；
- 每条评论的本次请求序号，例如 `C001`；
- 评论正文；
- 六个允许分类和输出结构说明。

不发送账号 ID、作品 ID、评论 ID、本地 `commentKey`、作者身份、点赞数、回复数、评论时间、Cookie、登录态、机器信息或数据库路径。

### 7.3 结构化输出

AI 必须返回：

- 每个请求序号对应的一个或多个分类；
- 最多 5 个选题候选；
- 每个候选的标题、简短理由和一个或多个证据序号。

本地适配器把请求序号映射回 `commentKey`，并逐项校验：

1. 分类只能来自六个允许值；
2. 评论序号必须属于本次发送集合；
3. 候选数量不得超过 5；
4. 每个候选至少引用一条存在于本地数据库的原评论；
5. 重复、未知或空引用视为结构错误；
6. 任一候选证据不合法时，整次 AI 洞察不落库，不能保留部分看似成功的结果。

分类和候选都是辅助判断，不自动改变内容计划。用户查看原评论后自行决定是否采用选题。

## 8. 事务与失败边界

评论保存和 AI 分析是两个先后独立的事务：

1. 评论采集完成并通过合同校验；
2. 评论同步运行与评论证据原子提交；
3. 如果 AI 已配置，再读取刚提交的评论生成洞察；
4. AI 成功后单独保存洞察；
5. AI 失败只把洞察运行标为失败，不能回滚或隐藏已保存评论。

平台同步失败时保留上次成功评论。重新同步只由用户再次点击触发，不做后台无限重试。

固定公开错误码：

- `comment_content_unavailable`：作品列表或所选作品不可用；
- `comment_login_required`：登录态失效；
- `comment_verification_required`：平台要求人工验证；
- `comment_access_denied`：当前账号无评论读取权限；
- `comment_payload_invalid`：官方响应不符合已验证合同；
- `comment_sync_timeout`：本次只读同步超时；
- `comment_sync_cancelled`：退出或用户取消；
- `comment_ai_not_configured`：AI 未配置，评论仍可用；
- `comment_ai_timeout`：AI 请求超时；
- `comment_ai_service_unavailable`：AI 服务不可用；
- `comment_ai_response_invalid`：AI 输出结构不合格；
- `comment_ai_evidence_invalid`：AI 引用不存在的评论证据。

界面、数据库和日志只出现固定错误码与固定中文说明，不出现原始异常、URL、查询串、响应正文、凭据或本机路径。

## 9. 界面

数据监测页保留现有平台、账号、日期范围和指标区。作品表改为单行选择，并在表格下方增加“评论洞察”面板。

未选择作品时：

- “同步最新评论”按钮不可用；
- 面板提示“请先选择一篇作品”。

选择作品后：

- 显示作品标题和最近评论同步时间；
- 提供“同步最新评论”和“AI 设置”；
- 显示同步进度的固定阶段：准备会话、读取评论、校验、保存、生成洞察、完成；
- 评论列表显示正文、点赞数、回复数和时间，不显示任何作者信息；
- 支持按六类标签筛选；
- 选题候选可展开查看其引用的原评论；
- 页面中不出现回复、删除、点赞、发布等动作按钮。

如果抖音作品列表仍未取得，面板明确显示“抖音作品列表尚未取得，暂时无法同步评论”，不能把账号没有作品作为解释。

## 10. 并发、退出与数据刷新

- 同一账号同一作品同一时间只允许一个评论同步；
- 账号指标同步与评论同步可按现有后台任务管理器排队，但不能共享浏览器页面；
- 切换账号、平台或作品时，旧任务结果只写入它原本的账号和作品，不得渲染到当前选择；
- 关闭客户端时沿用现有收束屏障，等待评论采集器关闭；超时后标记 `comment_sync_cancelled`；
- 常规“同步数据”只同步账号和作品指标，不读取评论正文；
- 只有评论数量增加或用户主动选择作品时，界面可以提示“有新评论可同步”，但仍须用户点击后才读取正文。

## 11. 测试阶梯

实现采用小步测试，不在每个修改后跑全量：

1. 数据合同测试：真实响应脱敏夹具、域名和路径白名单、作者字段丢弃、一级评论、游标和上限；
2. 模型测试：严格类型、非负计数、时间格式、匿名键、重复行和未知字段；
3. 数据库测试：迁移、事务回滚、去重、计数更新、历史保留和级联删除；
4. 服务测试：首次 100 条、遇到已知评论停止、平台失败保留旧数据、AI 失败不回滚评论；
5. AI 测试：只发送允许字段、多标签、最多 5 个候选、未知证据、重复证据、超时、无 Key 和原始响应不落库；
6. UI 测试：作品单选、按钮状态、固定进度、分类筛选、证据展开、过期任务不串账号、不出现写操作；
7. 生命周期测试：重复点击、切换页面、客户端退出和浏览器资源清理；
8. 相关测试通过后跑数据监测受影响模块；
9. 收尾时再跑一次全量测试。

设计前基线已经通过抖音采集、平台数据服务、平台同步和数据监测页共 123 项相关测试。该结果只证明现有底座未坏，不证明评论功能已经实现。

## 12. 真实验收

本地测试通过后，使用用户明确授权的已登录抖音账号做一次只读验收：

1. 选择一篇官方后台可见且至少有 5 条评论的作品；
2. 同步后，一键发中的正文、点赞数、回复数和时间与官方页面逐条一致；
3. 页面和数据库中不存在作者头像、昵称和用户 ID；
4. 第二次同步不产生重复评论，并能更新已知评论的点赞或回复数量；
5. AI 已配置时，最多显示 5 个候选，每个候选展开后都能看到数据库中的真实原评论；
6. AI 未配置或故意超时时，评论仍显示为同步成功；
7. 退出客户端后没有残留 Chromium 或 Playwright 会话；
8. 全程未向抖音执行回复、删除、点赞或发布。

在完成这次真实账号验收前，只能说“本地实现和脱敏合同测试完成”，不能说评论洞察已经在抖音真实可用。

## 13. 版本与交付

本轮设计文档不修改应用版本。正式实现开始时，先把统一版本从 `0.4.2` 升级到 `0.4.3`，并保证应用内版本、macOS 包、Windows 包名和构建信息一致。后续每次客户端更新继续在提交和打包前自动递增版本号。
